프롬프트의 완료 기준 10항목을 **통과 / 실패 / 미검증**으로 구분해 적습니다.
"했다"고만 적지 않고, 어떻게 쟀는지와 무엇을 못 쟀는지를 함께 남깁니다.

측정 환경: Windows 11, Node 24.16.0, `wrangler dev --local` (workerd),
같은 컴퓨터 안의 loopback 연결. 날짜 2026-09-20.

```bash
npm run dev:worker &                        # 아래 세 가지는 서버가 떠 있어야 한다
npm run dev:host &
npm run e2e -- --students 4
npm run test:embed
npm run loadtest -- --students 100 --map classic-night --rule last
```

## 1. 교사 1명 + 분리된 학생 3개 이상이 같은 결과를 받는가 — **통과**

`npm run e2e` 가 **연결을 따로따로 맺어** 확인합니다(같은 브라우저의 탭 공유가 아닙니다).
각 학생은 독립된 WebSocket 이고 서로 다른 `participantId` 를 받습니다.

```
✓ 학생 4명이 각자의 연결로 들어간다
✓ 학생마다 서로 다른 참가자 id 를 받는다
✓ 모든 학생이 같은 라운드의 카운트다운을 받는다
✓ 학생 4명이 교사와 똑같은 결과(eventId)를 받는다
✓ 당첨자 목록이 모든 화면에서 같다
```

브라우저로도 교사 화면 + 학생 화면(모바일 크기)을 동시에 띄워 같은 경기를 보는 것을
확인했습니다.

> **주의해서 봐야 할 점**: 같은 브라우저에서 학생 탭을 여러 개 열면 `localStorage` 를
> 공유해 **같은 참가자**로 들어갑니다(재접속 자격이 같기 때문). 그래서 여러 학생 검증은
> 브라우저 탭이 아니라 독립 연결로 했습니다. 실제 교실은 기기가 다르므로 문제가 없습니다.

  > ⚠ **이 진단은 절반만 맞았습니다.** 경고 문구는 이걸로 사라졌지만, 29초를 기다린
  > **진짜 원인은 따로 있었고 그대로 남아 있었습니다.** 아래 「배포 뒤에 잡은 버그」를

- **「다음 라운드 준비」를 눌러도 결과가 안 사라짐** — 치운 결과를 기억하지 않았습니다.
- **교사 기본 카메라가 「전체 보기」였음** — 네온 장거리(세로 275칸)에서는 구슬이 좁쌀만
  해집니다. 기본을 「선두 따라보기」로 바꿨습니다.

## 4. 모든 맵 × 여러 시드 × 1·2·8·30·60·100명 자동 시뮬레이션 — **통과**

```
맵 8개 × 인원 [1, 2, 8, 30, 60, 100] × 시드 3개 = 144판
문제 없음. 가장 오래 걸린 한 판의 계산 시간 2001ms
```

찾은 것: 벽 이탈 **0건**, 제한시간 초과(영구 정체) **0건**, 결승 순서 뒤집힘 **0건**,
포털 상한 도달 **0건**.

### 완주 시간 (30명 기준: 첫 도착 / 절반 / 전원)

| 맵 | 첫 | 절반 | 전원 |
|---|---|---|---|
| 회전 관문 | 11.0초 | 19.1초 | 52.9초 |
| 버블 계곡 | 14.1초 | 16.0초 | 20.8초 |
| 항아리 탈출 | 5.4초 | 23.6초 | 72.1초 |
| 네온 장거리 | 19.5초 | 26.2초 | 36.8초 |
| 바람 협곡 | 12.0초 | 17.6초 | 27.6초 |
| 포털 연구소 | 12.0초 | 17.6초 | 30.8초 |
| 자석 공장 | 18.2초 | 25.5초 | 91.4초 |
| 종합 운동장 | 12.5초 | 23.0초 | 90.5초 |

**확장 맵 목표(30~90초)에 대한 솔직한 평가**:
「전원 도착」기준으로 바람 협곡(27.6초)은 목표보다 짧고, 자석 공장(91.4초)과
종합 운동장(90.5초)은 목표 상단에 걸칩니다. 실제 라운드는 규칙이 요구한 만큼만
도착하면 끝나므로(「첫 번째」면 12~18초), 교사가 체감하는 길이는 더 짧습니다.
맵 카드에 「첫 도착 ~ 전원 도착」 범위를 그대로 적어 두었습니다.

기본 4개는 원본 배치를 계승했으므로 시간을 억지로 맞추지 않았습니다.
항아리 탈출의 전원 도착 72초는 원본의 「휘저어지는 항아리」 구조에서 나오는 값입니다.

### 성능 (측정 조건)

Node 24, 단일 스레드, 화면 없음. 한 판을 **가능한 한 빨리** 돌렸을 때의 계산 시간입니다.

- 가장 무거운 한 판: 2001ms (항아리 탈출, 100명)
- 네온 장거리(장애물 267개) 100명: 약 1000ms

실제 경기는 실시간으로 도므로(1초를 1초에), 이 값은 「여유가 얼마나 있는가」를 뜻합니다.
30초짜리 경기를 2초에 계산할 수 있다는 것은 실시간 대비 약 15배의 여유입니다.

## 5. 지연·재연결·늦은 입장·교사 끊김 — **통과**

`e2e` 가 경기 도중에 실제로 일으켜 확인합니다.

```
✓ 경기 중에도 새 학생이 들어올 수 있다
✓ 늦게 온 학생은 이번 라운드 명단에 없다      (관전 → 다음 라운드부터 참가)
✓ 끊겼던 학생이 같은 참가자로 돌아온다        (재접속 자격으로 복구)
✓ 다른 런타임이 호스트를 잡으면 세대가 올라간다
✓ 옛 호스트의 메시지는 거절된다
```

교사 새로고침은 런타임 id 가 바뀌므로 서버가 진행 중이던 라운드를 **취소**하고
재경기를 안내합니다(결과를 짐작해 복원하지 않습니다). 교사 연결만 끊긴 경우에는
`paused` 로 두고 「연결이 돌아오면 이어집니다」를 전체 화면에 띄웁니다.

교사 탭 비활성화에 따른 타이머 지연은 물리 Worker 가 감지해 교사 화면에 띄웁니다
(브라우저에서 실제로 동작을 확인했습니다 — 위 2번의 고친 것 참고).

## 7. 60명 부하 · 100명 스트레스 — **통과**

**구슬을 100개 그린 것이 아니라 연결을 100개 맺은** 시험입니다.
한 연결이 한 기기를 흉내 냅니다.

| | 60명 (버블 계곡) | 100명 (네온 장거리, 「마지막 도착」) |
|---|---|---|
| 전원 접속까지 | 0.43초 | 0.65초 |
| 경기 길이 | 14.2초 | 39.2초 |
| 교사→서버 프레임 | 131장 · 136KB | 358장 · 626KB |
| 학생 한 명이 받은 양 | 135KB | 623KB |
| 프레임 지연 (중앙/p95/최대) | 10 / 18 / 48ms | 15 / 27 / 142ms |
| 결과 도달 | 60/60명, 같은 eventId | 100/100명, 같은 eventId |
| 결과가 전원에게 퍼진 시간 | 9ms | 30ms |

100명 기준 학생 한 명당 약 **16KB/초(≈128kbps)** 입니다. 저화질 영상 한 줄기보다 적지만,
100명이 동시에 받으면 교실 전체로는 약 12.8Mbps 입니다. 요즘 교실 무선 공유기에는
무리가 없는 양이지만, 오래된 장비라면 미리 확인하는 편이 좋습니다.

> **이 시험이 재지 못한 것**: 같은 컴퓨터의 loopback 연결이라 실제 무선망의 손실·지연,
> 휴대폰의 그리기 성능, 공유기의 동시 접속 한계는 재지 못했습니다.
> 실제 교실에서 한 번 돌려 보는 것을 대신하지 못합니다.

- 색 외에 상태를 알 수 있게 했습니다 — 개폐문의 「열림/닫힘」 글자, 바람의 화살표와

> **미검증**: **실제 휴대폰·태블릿으로는 확인하지 못했습니다.** 위는 전부 데스크톱
> 브라우저의 화면 크기 에뮬레이션입니다. 터치 반응, 실제 글꼴 크기, 저사양 기기의
> 그리기 성능은 실제 기기로 따로 확인해야 합니다.
> 360px 폭은 CSS 에 대응(`@media (max-width: 400px)`)했지만 실제로 띄워 보지는 않았습니다.

## 9. 예제 수업 앱 연동 — **통과**

브라우저에서 한 바퀴 돌렸습니다.

1. 「활동 열기(교사)」 → 예제 **서버**가 공유 비밀로 방을 만들고 교사 티켓을 서명
2. iframe 이 `available`(기능 7개) → SDK 가 `mount` → 티켓 검증 → `ready`
3. 「명단 넘기기」 → 8명이 들어감
4. 「규칙 보내기」(버블 계곡 / 상위 3명) → 「경기 시작」
5. `roundFinished`(화면용)가 옴 → 화면에는 「결과 확인 중」
6. **활동 서버가 서명한 webhook 이 예제 서버에 도착** → 검증 후 기록
   → 「1위 최지우 — 발표자, 2위 윤서아, 3위 정민서」

`npm run test:embed` 가 경계를 확인합니다.

```
✓ 공유 비밀 없이는 연동 방을 못 만든다
✓ 틀린 비밀로도 못 만든다
✓ 등록되지 않은 연동 id 를 거절한다
✓ 서명이 틀린 티켓을 거절한다
✓ 만료된 티켓을 거절한다
✓ 지난 활동의 티켓을 거절한다
✓ 다른 앱을 가리키는 티켓을 거절한다
✓ role 글자만으로는 교사가 되지 않는다
✓ 학생 티켓으로 교사 화면을 달라고 해도 학생 권한만 준다
✓ 서명 없는 결과는 기록되지 않는다
✓ 서명은 맞지만 지난 활동의 결과는 기록되지 않는다
```

### 이 과정에서 찾아 고친 것

- **`setParticipants`·`startRound` 가 「아직 방에 연결되지 않았습니다」만 돌려줌** —
  `message` 리스너가 첫 렌더의 처리 함수를 붙들고 있었습니다(stale closure).
  ref 를 거쳐 늘 최신 함수를 부르도록 고쳤습니다.
- **`setConfig` 가 서버에 못 보내고도 성공이라고 답함** — 조용히 화면에만 반영하면
  부모 앱은 규칙이 바뀐 줄 알고 시작을 누릅니다. 이제 명시적으로 실패합니다.

## 배포 뒤에 잡은 버그

### 「경기 시작」을 눌러도 한참 뒤에 출발 (2026-09-20, 고침)

**증상**: 교사가 시작을 눌러도 구슬이 출발하지 않다가 한참 뒤에 출발했다.

**원인**: 메인 스레드의 `performance.now()` 값을 Web Worker 에 그대로 넘겼다.
`performance.now()` 의 기준점(`timeOrigin`)은 **컨텍스트마다 다르다** — 메인 스레드는
페이지를 연 시각이 0 이고, 워커는 워커가 만들어진 시각이 0 이다. 실제로 재어 보니
같은 순간에 메인은 568,237ms, 워커는 16ms 였다.

그래서 워커는 「페이지를 열어 둔 시간 + 카운트다운」 만큼 기다린 뒤에야 출발했다.
**지연 시간 = 교사가 그 화면을 열어 둔 시간.** 새로고침 직후에 누르면 멀쩡했기 때문에
처음 검증에서 놓쳤고, 29초가 걸린 한 번은 「탭 절전으로 인한 타이머 지연」으로 오진해
경고만 지웠다. 증상을 덮고 원인을 그대로 둔 것이다.

**고친 것**: 경계를 넘는 시간은 **길이(ms)** 로만 주고받는다. 절대 시각은 그 값을 만든
컨텍스트 안에서만 쓴다.

- 메인 → 워커: `startAt`(절대) → `startDelayMs`(길이)
- 서버 → 화면: 카운트다운에 `countdownMs`(길이)를 함께 실어 보내고, 받는 쪽은
  제 시계로 다시 잡는다. 교실 PC 의 시계가 어긋나도 흔들리지 않는다.
- `apps/web/src/race/timing.ts` 에 가드를 모았다. 길이 자리에 절대 시각처럼 보이는
  값이 오면 **0 으로 보고 바로 출발**한다(상한으로 깎으면 15초를 멀거니 기다리게 된다).

**재발 방지 검사**: `apps/web/src/race/timing.test.ts` 10건.
실제로 터진 값(568,237 + 3,000)을 그대로 넣어 0 이 나오는지 본다.

**확인**: 페이지를 74초(로컬)·57초(운영) 열어 둔 뒤 시작을 눌러, 클릭에서 출발까지
2.2초·2.9초가 걸리는 것을 확인했다(카운트다운 3초 안). 고치기 전이라면 77초·60초였다.

## 알려진 한계

- **교사의 결과 조작은 막지 못합니다.** 물리가 교사 브라우저에서 돌기 때문입니다.
  이것은 「교사를 믿는 교실용 모델」입니다(`docs/architecture.md`).
- **같은 시드라도 다른 기기에서 같은 결과가 나온다고 보장하지 않습니다.**
  그래서 한 호스트가 계산하고 나머지는 받아 봅니다.
- **완전히 균등한 확률이라고 주장하지 않습니다.** 출발 자리와 장치 때문에 미세한
  차이가 있을 수 있어, 매 라운드 자리를 섞습니다(`docs/rules.md`).
- **로그인 없이 기기를 바꾼 동일인을 가려내지 못합니다.** 기기가 바뀌면 새 참가자가
  됩니다. 화면에도 그렇게 안내합니다.
